SECTION 1: META'S PLATFORM AND SCALE CHALLENGES
========================================================================

FACEBOOK AT BILLIONS OF USERS

Meta (formerly Facebook) operates at planetary scale serving billions of users daily. This scale creates unique technical challenges and requires novel solutions.

Global reach: Users in every timezone, thousands of languages, diverse network conditions. Bandwidth-limited regions must be supported. Latency optimization is critical—every millisecond of improvement affects user engagement.

Real-time requirements: News Feed must reflect latest actions immediately. Comments, likes, shares propagate within seconds. This creates consistency challenges at scale.

Data volume: Each user generates hundreds of KB of data daily (actions, interactions, content). Multiply by 3 billion users, you get petabytes daily that must be processed, stored, analyzed.

Reliability: downtime is unacceptable. When Facebook is down, millions of users can't communicate. High availability is mandatory, not optional.

SECTION 2: THE SOCIAL GRAPH AND TAO
========================================================================

UNDERSTANDING THE SOCIAL GRAPH

The social graph is the fundamental data structure at Meta: nodes are people, edges are relationships (friendships, follows, pages followed). Nearly all features depend on efficient graph queries.

Graph characteristics:
- Highly connected: average person has ~300-500 friends, follows ~200 pages
- Sparse: only small fraction of all possible edges exist
- Dynamic: edges added/deleted constantly as people connect/disconnect
- Diverse: friendship (symmetric) vs follow (asymmetric), group membership, page follows

Graph queries:
- Adjacency: get friends/followers of person
- Path finding: are two people connected? Shortest path?
- Influence: who influences person? Reach analysis?
- Common neighbors: mutual friends between two people

Naive implementation: store in RDBMS with users table and friendships table.
```
users: user_id, name, email
friendships: user_id, friend_id
Query friends: SELECT friend_id FROM friendships WHERE user_id = ?
```

Problem: billions of users × 500 average friends = 1.5 trillion edges. Querying any user's friends is expensive. Storing and querying requires sophisticated systems.

TAO: THE ASSOCIATION AND OBJECT DATA STORE

TAO is Meta's distributed, in-memory cache and database for the social graph. Handles billions of association queries per second.

Architecture:
- Objects: entities with properties (users, pages, comments)
- Associations: relationships between objects (friendship, follows)
- Sharding: objects sharded by id modulo number of servers
- Caching: associations cached in memory after first read

Sharding strategy:
- User 123 shards to server 123 % num_servers
- All objects for user 123 go to same server
- Enables efficient batching: get all user's friends from same server
- Consistency: same server owns all data for user, no distributed transactions

Consistency:
- TAO is eventually consistent with write-through to database
- Writes go to database immediately, cache updated asynchronously
- Reads return from cache (possibly stale) or database if cache miss
- Staleness is bounded: re-cache periodically

Query types:
- getObject: fetch object by id
- getAssociations: fetch associations (edges)
- assocRange: get range of associations (e.g., oldest N friends)

Replication:
- Master server owns object
- Replicas cache for reads
- Writes go to master
- Replicas eventually get updates

Power of TAO: enables instant lookups for any social query. "Get friends of X" is single cache hit. "Get friends of X who like Y" requires post-processing but foundational lookup is instant.

SECTION 3: NEWS FEED: RANKING AT SCALE
========================================================================

NEWS FEED ARCHITECTURE

News Feed is centerpiece of Facebook experience. Billions of users create trillions of potential stories daily. Feed must:
- Be personalized (your closest friends' recent activity ranked highest)
- Be fresh (new content appears within seconds)
- Be diverse (avoid echo chambers, show varied content)
- Load quickly (feed loads in < 1 second)

Pipeline architecture:
1. Generation: identify candidate stories from people/pages followed
2. Ranking: score stories by relevance, engagement potential
3. Filtering: remove sensitive content, apply privacy rules
4. Serving: return top N stories

CANDIDATE GENERATION

For each user, which stories to consider?
- Brute force: all stories from all connections (3B users × 500 friends = 1.5T stories/second)
- Impossible at scale

Practical approach:
- Real-time generation: only stories from recent activity
- Pre-ranked candidates: store high-signal candidates separately
- Multi-tiered fetching: fetch thousands of candidates, rank down to dozens

Engagement signals used:
- Recency: newer stories generally better
- Authority: stories from important people (many followers, friends)
- Social proof: stories with many likes/comments rank higher
- Content quality: text, photos, videos have different engagement rates

RANKING ALGORITHM

Feed ranking is machine learning problem at scale. Candidate stories scored by trained model, top stories returned.

Features for ranking model:
- User features: age, location, preferences, history
- Content features: type (photo/text/video), language, topic
- Social features: author popularity, common friends, engagement history
- Context features: time of day, device type, network type

Model training:
- Historical data: billions of historical feed views and engagements
- Labels: whether user engaged with story (liked, clicked, shared, etc.)
- Optimization: maximize engagement (clicks/day is proxy for satisfaction)

Challenges:
- Model must score 100M stories in seconds for each user
- Stale features: ranking must use live data, but model training uses historical data
- Long-tail problem: many stories have few historical examples
- Diversity: optimizing only for engagement creates filter bubbles

DIVERSITY AND FILTER BUBBLE PREVENTION

Ranking purely by predicted engagement creates filter bubbles: users see only content confirming existing beliefs.

Solutions:
- Explicit diversity: ensure feed includes stories from diverse viewpoints
- Exploration: occasionally show lower-ranked stories to gather engagement signals
- Community standard diversity: ensure users exposed to communities outside their existing circles
- Content quality: demote low-quality content even if engaging

This is intrinsically a trade-off: purely optimal engagement is more likely to be filter bubble. Meta consciously reduces engagement to maintain diversity.

SECTION 4: HAYSTACK: PHOTO STORAGE AT SCALE
========================================================================

THE PHOTO STORAGE PROBLEM

Billions of photos uploaded daily. Each photo has multiple versions (thumbnail, medium, full resolution). Requirements:
- Availability: rarely deleted, must always retrieve
- Durability: photos lost = unacceptable
- Throughput: billions of accesses daily
- Latency: photo loads in <1 second
- Cost-effectiveness: billions of photos means cost per photo matters

Naive approach: S3 or similar object store. Works but expensive—each photo lookup hits distributed filesystem, network overhead for billions of accesses.

HAYSTACK ARCHITECTURE

Haystack is Meta's photo storage system optimizing for billion-scale access.

Key innovation: batch photos into files, use memory index.

Architecture:
- Photo storage directory server: maps (photo_id, version) → (storage_server, file_id, offset)
- Storage server: stores batches of photos in single file
- Append-only files: photos appended to file, no overwrites
- Memory index: (photo_id → file position) cached in memory

Lookup flow:
1. Client has photo_id, requests from directory server
2. Directory server returns (storage_server, file_id, offset, size)
3. Client requests from storage_server at (file_id, offset, size)
4. Storage server uses file_id to locate file on disk
5. Random access at offset retrieves photo

Efficiency gains:
- Directory server maps to file offset (O(1) lookup via hashtable in memory)
- No filesystem metadata lookups (huge latency reduction)
- Batch photos in single file (efficient disk reads, sequential access where possible)
- Append-only writes (write buffering, batch flushes)

Durability:
- Replicate photo files across datacenters
- 3x replication: survive 2 simultaneous failures
- Warm replicas: ready to serve immediately on failure

Compaction and cleanup:
- Deleted photos leave holes in files
- Offline compaction: reorganize files, remove gaps
- Logical deletion: mark as deleted in index without immediate disk cleanup
- Garbage collection: physical deletion happens periodically

Scavenging:
- Periodically check if reference still exists (photo might be deleted)
- Remove unreferenced photos from disk

Cache considerations:
- Most popular photos cached in edge caches
- Less popular photos accessed from origin occasionally
- Photo cache hit rate 80%+

SECTION 5: MEMCACHE AT FACEBOOK SCALE
========================================================================

CACHING ARCHITECTURE DECISIONS

Memcache (Redis) is critical to Meta's performance. Distributed in-memory cache reduces database load dramatically.

Single cache instance limitations:
- Limited capacity: server has finite memory
- Single point of failure: if down, all cache lookups fail
- Single server saturates at ~200K requests/sec

Distributed cache:
- Many servers, each holds portion of data
- Client hashes key to determine server
- Horizontal scaling: add servers, rehash some keys

Challenges at Meta scale:
- Billions of cache entries
- Trillions of cache operations/day
- Failure of single cache server should be survivable
- Replication adds consistency complexity

REPLICATION AND CONSISTENCY

Replica groups: multiple copies of cache for fault tolerance.

Setup:
- Primary replica: handles writes and reads
- Secondary replicas: handle reads only
- On primary failure, secondary promoted

Consistency complexity:
- Write to primary: when return to client?
  - Immediately (risky: might fail during replication)
  - After primary stores (might lose if primary fails before replica gets it)
  - After N replicas confirm (safe but slow)
- Meta chose probabilistic consistency: update primary, asynchronously replicate, expose risk

Leader-based replication (master-slave):
- Master: single writer, replication source
- Slaves: read-only, receive updates asynchronously
- Write strong consistency: always go to master
- Read consistency: stale data possible from slaves (eventual consistency)

Failover: on master failure, elect new master among slaves.

PERFORMANCE OPTIMIZATION

Batching requests: instead of one request per item, batch 100+ requests to single round-trip.

Connection pooling: reuse TCP connections to cache servers rather than opening new connection per request.

Compression: serialize complex objects to bytes, compress if large.

Lua scripting: perform complex operations server-side rather than round-tripping.

SECTION 6: REACT AND FRONTEND SYSTEMS
========================================================================

REACT: COMPONENT-DRIVEN UI

React revolutionized frontend by introducing components: reusable UI pieces with encapsulated state and rendering logic.

Virtual DOM:
- Representation of actual DOM in memory
- React updates VDOM, diffs with previous VDOM
- Only changed elements updated in actual DOM
- Avoids expensive direct DOM manipulation

Rendering flow:
1. Component state/props change
2. React re-renders component to new VDOM
3. Diff algorithm compares old VDOM to new VDOM
4. Batch minimal DOM updates
5. Browser repaints affected pixels

Fiber architecture (modern React):
- Break rendering into units of work (fibers)
- Work can be interrupted, allowing high-priority updates (user input) to jump ahead
- Async rendering: render can happen over multiple frames
- Better responsiveness than synchronous rendering

Key concepts:
- Components: functions/classes that return JSX (UI description)
- Props: input to component, immutable
- State: mutable data owned by component
- Hooks: functions accessing state and effects (useState, useEffect, etc.)
- Effects: side effects (API calls, subscriptions) run after render

Optimization:
- Memoization: avoid re-rendering if props unchanged
- Code splitting: lazy load components
- Suspense: wait for async data before rendering
- Concurrent rendering: prioritize user-visible updates

Meta uses React for Facebook, Instagram, Threads UIs. Understanding React is critical for frontend roles at Meta.

FRONTEND PERFORMANCE

Performance metrics:
- Largest Contentful Paint (LCP): when main content visible, < 2.5 seconds desired
- First Input Delay (FID): latency to respond to user input, < 100ms desired
- Cumulative Layout Shift (CLS): unexpected layout changes, < 0.1 desired

Optimization techniques:
- Code splitting: load only code needed for current page
- Lazy loading: load images/components when needed
- Compression: gzip JavaScript and CSS
- Minification: remove unnecessary characters
- Browser caching: cache static assets
- CDN: serve from edge near user
- Image optimization: serve right size for device

SECTION 7: MICROSERVICES AND DISTRIBUTED SYSTEMS AT META
========================================================================

SERVICE ARCHITECTURE

Facebook migrated from monolith to microservices to enable independent scaling and deployment.

Service decomposition:
- Friends service: handles friendship queries
- Feed service: generates personalized feeds
- Photo service: stores and retrieves photos
- Messaging service: handles direct messages
- Commerce service: handles shop/marketplace
- Auth service: handles authentication

Benefits:
- Independent scaling: scale heavy services without scaling others
- Technology choice: each service picks best tools
- Independent deployment: ship feature without touching entire codebase
- Fault isolation: service failure doesn't crash entire platform

Challenges:
- Distributed system complexity: network calls fail, latency exists
- Data consistency: distributed transactions hard
- Service discovery: services appear/disappear
- Monitoring: harder to track issues across services

Communication patterns:
- Synchronous (REST/gRPC): request-response, blocking, tightly coupled
- Asynchronous (Kafka/RabbitMQ): events, decoupled, enables buffering

Service discovery: services register with registry (Consul, Eureka), clients look up dynamically. Enables adding/removing services without configuration changes.

Circuit breaker pattern: wrap calls to external services. Track failure rate in rolling window. When exceeds threshold, "open" circuit—fail fast without calling service. Half-open state periodically tests recovery.

API Gateway: single entry point for clients. Handles:
- Authentication: verify client identity
- Rate limiting: prevent abuse
- SSL termination: encrypt client connection
- Request routing: route to appropriate service
- Response transformation: adapt format for client

SECTION 8: REAL-TIME SYSTEMS AT FACEBOOK SCALE
========================================================================

ONLINE VS OFFLINE SYSTEMS

Online systems: respond immediately (< 100ms), serve live traffic, directly impact user experience.

Offline systems: batch processing, compute-intensive, can take hours, no tight latency requirements.

Typical architecture: online system generates events, offline system processes later for insights.

Example: feed ranking. Online: show feed in seconds. Offline: analyze data, train better ranking model, deploy new model.

NOTIFICATION SYSTEMS

How does user learn of activity? Through notifications.

Challenge: billions of users, millions of events per second, different notification preferences.

Architecture:
- Event generation: user action creates event (like, comment, tag)
- Event aggregation: combine related events (5 people liked post)
- Notification generation: decide to notify user? Which channel?
- Delivery: send via push notification, email, SMS

Channels:
- Push notification: delivered to phone immediately
- Email: less urgent, daily digest possible
- SMS: most urgent, reserved for important
- In-app: only when app open

Personalization: user preferences determine channels. Some users prefer push, others prefer email.

Spam prevention: aggressive notification = worse engagement. Only notify when relevant.

SECTION 9: MACHINE LEARNING AT META
========================================================================

FEATURE PLATFORMS

Feature platform: centralized system storing features for ML models.

Motivation: many models need same features (user age for feed, comments, search). Recompute each time wastes resources. Store once, reuse.

Architecture:
- Feature store: database of precomputed features
- Feature engineering: code that computes features from raw data
- Serving layer: low-latency access to features for online models
- Monitoring: track feature distributions, detect staleness

Features stored with ownership, versioning, monitoring.

MODEL LIFECYCLE

Experimentation: data scientists develop models, test ideas.

Staging: model tested on hold-out data, validated.

Deployment: model pushed to production, serves small traffic initially.

Rollout: gradually increase traffic to model, monitor metrics.

Monitoring: track model predictions, compare to ground truth, detect degradation.

Retraining: periodically retrain model on new data.

DEEP LEARNING AT SCALE

Deep neural networks: many layers enabling powerful pattern recognition.

Challenges at Meta scale:
- Model size: billions of parameters, doesn't fit on single GPU
- Training time: billions of examples, training takes days/weeks
- Inference latency: must serve predictions milliseconds

Solutions:
- Distributed training: train on many GPUs/TPUs in parallel
- Model compression: quantization, pruning, distillation for inference
- Caching: cache predictions to avoid repeated computation

SECTION 11: DATA INFRASTRUCTURE AT META
========================================================================

SCRIBE: EVENT LOGGING PIPELINE

At Meta scale, understanding what users do requires analyzing trillions of events. Scribe is the distributed logging infrastructure.

Architecture:
- Client libraries: instrument code to log events
- Aggregation: collect logs from thousands of servers
- Processing: parse, filter, route events
- Storage: store in distributed filesystem for analysis
- Analytics: query logs to understand system behavior

Event payload:
- Timestamp: when event occurred
- User ID: which user triggered event
- Event type: what action (like, comment, share, etc.)
- Event properties: additional context (object id, location, device)

Challenges:
- Scale: trillions of events/day across billions of users
- Real-time: need access to events immediately for dashboards
- Retention: store events long-term for historical analysis
- Cost: storing terabytes of logs is expensive

Solutions:
- Compression: reduce event size via compression
- Sampling: only log 1% of events for less critical paths
- Partitioning: partition logs by time/user/type for efficient querying
- Tiered storage: hot data (recent) in fast storage, cold data (old) in cheap storage

REALTIME ANALYTICS

Dashboard showing current system state: how many likes/sec, how many comments, how many users online.

Challenges:
- Must update within seconds (not hours like batch analytics)
- Billions of events/second to process
- Accurate aggregations at huge scale

Architecture:
- Event streaming: events flow from logging to real-time aggregation
- Mini-batches: aggregate events in 10-second windows
- Distributed aggregation: many servers aggregate their portion
- Merging: combine partial results into final answer

Example: "How many likes in last minute?"
1. Events arrive with like actions
2. Each server counts likes in its events
3. Every 10 seconds, servers send counts
4. Central aggregator sums counts from all servers
5. Total likes exposed via API or dashboard

HIVE: DATA WAREHOUSE

Historical analysis requires querying massive datasets. Hive is Meta's data warehouse (built on Hadoop/HDFS).

Characteristics:
- Petabytes of data: years of historical events
- SQL interface: query data like database
- Distributed processing: queries run on thousands of cores in parallel
- Batch: queries take minutes to hours (not real-time)

Use cases:
- "How many new users joined last month?"
- "Which content types get highest engagement?"
- "How does engagement vary by geography?"
- "Which features drive retention most?"

Query optimization:
- Partitioning: data partitioned by date, allows skipping old data
- Indexes: create indexes on common query columns
- Sampling: test queries on 1% sample before running on full data
- Caching: cache common query results

SECTION 12: RELIABILITY AND RESILIENCE PATTERNS
========================================================================

FAILURE IS INEVITABLE

At Meta scale, failures are constant: servers fail, network partitions occur, software bugs exist. The question is not "if" but "when."

Types of failures:
- Hardware: disk failures, power failures
- Network: link failures, packet loss, latency
- Software: bugs, memory leaks, performance degradation
- Human: misconfiguration, bad deploy

Cascading failures: one failure triggers others. Service A slow → Service B times out → Service C retries → traffic amplification → cluster overloaded.

REDUNDANCY AND REPLICATION

Defense against failures: replicate data and services.

Replication strategies:
- Synchronous: wait for replicas to confirm before returning (safe, slow)
- Asynchronous: return immediately, replicate in background (fast, risky)
- Quorum: wait for majority (balanced)

Consistency levels:
- Strong consistency: all replicas see same value
- Eventual consistency: replicas converge over time
- Causal consistency: related operations ordered correctly

Trade-off: consistency vs latency. Strong consistency = slower. Eventual consistency = faster but temporary inconsistency possible.

CIRCUIT BREAKERS AND GRACEFUL DEGRADATION

Circuit breaker pattern: wrap calls to external services. If service failing, open circuit—fail fast without calling.

States:
- Closed: normal, call service
- Open: service failing, reject requests immediately
- Half-open: allow test request to determine if service recovered

Graceful degradation: when service unavailable, degrade functionality instead of failing completely.

Example: Image not loading? Show placeholder. Ads unavailable? Show feed without ads. Personalization unavailable? Show chronological feed.

BULKHEADS

Isolate failures: contain damage from one failing service.

Strategy: separate resource pools for different services. If service A uses all threads, service B still has threads available.

Threadpool per service:
- Feed service: own threadpool
- Photos service: own threadpool
- Comments service: own threadpool
If Feed service hangs, only its threads affected.

RETRY STRATEGIES

Network failures are transient: retrying often succeeds.

But: retrying too aggressively can amplify failures.

Strategies:
- Exponential backoff: first retry after 100ms, next after 200ms, then 400ms, etc.
- Jitter: add randomness to backoff (prevents thundering herd)
- Max retries: give up after N retries

Example:
```
retry_count = 0
while retry_count < 3:
  try:
    return call_service()
  except NetworkError:
    retry_count += 1
    wait_time = (2 ^ retry_count) + random(0, 1000ms)
    sleep(wait_time)
throw_error("Service unavailable after retries")
```

SECTION 13: DEPLOYMENT AND RELEASE STRATEGY
========================================================================

CONTINUOUS DEPLOYMENT

Code ships multiple times per day. Features released, bugs fixed quickly.

Pipeline:
1. Code commit to repository
2. Automated tests run (unit, integration, system)
3. If tests pass, code built and packaged
4. Rolled out to canary (small percentage of servers)
5. Monitor metrics: errors, latency, engagement
6. If healthy, roll out to all servers
7. If problems, auto-rollback

Speed: from commit to production in hours.

CANARY DEPLOYMENTS

Minimize risk by rolling out to small percentage first.

Strategy:
- Deploy to 1% of traffic
- Monitor for errors, performance issues
- If good, increase to 5%
- Continue increasing: 5% → 10% → 50% → 100%
- If issues at any stage, rollback and investigate

Benefits:
- Catch bugs before affecting all users
- Rollback is fast (only affected 1-10% of users)
- Real traffic testing (no synthetic tests)

FEATURE FLAGS

Deploy code for feature but don't enable it immediately.

Approach:
- Code deployed with feature disabled
- Feature flag checked at runtime
- Product can enable for small percentage
- Monitor impact
- Gradually increase percentage

Benefits:
- Decouple deployment from release
- Quick rollback without redeploy
- A/B testing: enable for 50% test users

INFRASTRUCTURE AS CODE

Infrastructure defined in version control, reviewed, tested before deployment.

Tools:
- Terraform: describe infrastructure in code
- Ansible: automate configuration management
- Puppet/Chef: infrastructure automation

Benefits:
- Reproducible: same infrastructure every deployment
- Reviewable: infrastructure changes reviewed like code
- Versionable: history of changes

SECTION 14: TECHNICAL DEPTH: DIVING DEEP
========================================================================

SYSTEM DESIGN DEEP DIVES

When interviewing at Meta, expect system design questions for almost all roles.

Typical progression:
1. Design high-level system (architecture overview)
2. Dig into specific component (how does ranking work?)
3. Scale to real numbers (how many queries per second?)
4. Failure scenarios (what if cache fails?)
5. Optimization (how to reduce latency?)

Evaluation criteria:
- Decomposition: break problem into parts
- Trade-offs: understand and articulate trade-offs
- Calculations: do math correctly
- APIs: design clean interfaces
- Practical: solution works, not theoretical

Common bottlenecks to discuss:
- CPU: algorithm complexity
- Memory: data structures, caching
- Disk I/O: query patterns, indexing
- Network: bandwidth, latency, round-trips

OPTIMIZATION TECHNIQUES

When system is slow, where is time spent?

Profile first: measure before optimizing. Easy to waste time optimizing wrong thing.

Common optimizations:
- Caching: avoid recomputation
- Batching: reduce round-trips
- Indexing: faster lookups
- Compression: reduce transfer size
- Parallelization: use multiple cores/machines
- Algorithm selection: better algorithm > micro-optimizations

Example: feed loading slow?
1. Profile: where is time? Database? Cache? Network?
2. If database: add index, increase batch size
3. If cache: increase hit rate (what's in cache policy?)
4. If network: compress data, reduce round-trips
5. If client: parallelize requests, pre-fetch

DEBUGGING COMPLEX SYSTEMS

System behaving incorrectly: how to debug at Meta scale?

Techniques:
- Logs: instrument code, capture log at each step
- Metrics: graph behavior over time, spot anomalies
- Traces: follow request through all services
- Experiments: isolate variables, run controlled tests
- Code review: carefully read code with colleague
- Rubber duck debugging: explain problem to someone (or debugging duck)

Distributed system specific:
- Time synchronization: ensure clocks in sync (hard!)
- Network problems: distinguish packet loss from latency
- Cascading failures: failures trigger other failures
- Eventual consistency: data temporarily inconsistent

Meta interviews include behavioral components. Prepare stories using STAR format:

Situation: Set context
- "I was working on the recommendations team"
- "We were improving feed ranking quality"

Task: What was the goal/problem?
- "We needed to reduce recommendation latency"
- "Queries were taking 500ms, needed to get to 100ms"

Action: What did you do?
- "I analyzed query patterns"
- "Identified that we could cache common requests"
- "Implemented multi-tier caching strategy"

Result: What was the outcome?
- "Reduced query latency from 500ms to 50ms"
- "Improved feed load time by 40%"
- "System now handles 3x more concurrent users"

Prepare stories demonstrating:
- Ownership: you drove the project
- Impact: results you achieved
- Learning: what you learned from experience
- Collaboration: how you worked with others
- Handling failure: how you recovered from setbacks

SECTION 19: FINAL TIPS FOR SUCCESS
========================================================================

COMMUNICATION EXCELLENCE

Clarity:
- Explain your thinking process
- Name your assumptions explicitly
- Ask for clarification if confused
- Use specific examples

Depth:
- Go into details when appropriate
- Show you understand complexities
- Discuss tradeoffs of your approach
- Consider alternative solutions

CODE QUALITY

Correctness:
- Code should be syntactically correct
- Handle edge cases
- Test with multiple examples
- Walk through test cases

Style:
- Use meaningful variable names
- Organize code logically
- Comment complex logic
- Consistent formatting

SYSTEM DESIGN EXCELLENCE

Components:
- Break problem into parts
- Design each component
- Show how they interact
- Discuss failure modes

Scale:
- Understand numbers (QPS, storage, bandwidth)
- Do back-of-envelope calculations
- Design for billions of users
- Discuss caching, replication strategies

Tradeoffs:
- Understand consistency vs availability
- Latency vs throughput
- Cost vs reliability
- Simple vs powerful
